Decision Log

Caseware take-home · Pending product-template updates · Updated 2026-09-24

1. The problem

Caseware publishes product templates (one per product) shared by every firm; new versions ship roughly once a week. Each firm has hundreds of engagement files, and each engagement was created from one template at one version. Users need to see which engagements have a pending update and a human-readable summary to decide whether to apply or decline it.

  Template "Audit Canada"                 Firm "ABC"

     ├── v2                                  ├── Engagement "Jones 2026"  → Audit Canada  v4

The catch: the "Current" column exists, but it lives inside each engagement, and reading it costs ~1 minute per file.

"Reading the template information therefore requires loading the engagement, which is a slow operation (~1 minute per file; this should be treated as a hard constraint)."
"This database does not currently retain any information about Engagement files, which are stored in their own customer-specific databases."

300 engagements × 1 min = 5 hours. We need to know each engagement's version without opening it.

2. How key decisions were selected

A decision is key when all three hold: (1) the brief forces it, (2) there are real alternatives, (3) getting it wrong is expensive or breaks a non-functional requirement.
Not key: the stack (AWS is given), applying the update (out of scope), screen design (not requested).

4. Decisions

D1

Where "which version is each engagement on" comes from

Decided
Context (brief)
"Performance: opening a firm's engagement list, and finding out about a newly published update, cannot depend on loading engagement files synchronously."
"You may assume you can add hooks or events to any actions taken by either the product template storage system, or by the engagement management system."
Options
OptionVerdict
ALoad the files when the user opens the listRejected: hours of waiting; violates the performance requirement
BPeriodically rescan every engagementRejected: 1 min × engagement on every pass, almost all of it redundant; data hours stale
CEvent-fed engagement index + published-versions table + one-time backfillChosen
DChange engagement storage so the version is directly queryableRejected for now: invasive change to another system's core; kept as a future improvement
Decision

Three small tables owned by a new Pending Updates Service; pending = compare engagement_versions against template_releases, computed every time the list is read.

  • engagement_versions (what version each engagement is on): one row per engagement: template, current version, revision, declined-up-to, status (verifying / verified / error / archived). Written by the backfill and by engagement events; a new release never touches it.
  • template_releases (what versions Caseware has published): one row per published template version (template, version, published_at). Changes only when Caseware publishes. A new version never touches engagement_versions: it shows up as pending the next time the list is read.
  • decision_log (what the firm has decided): append-only, one row per decision: date, engagement, user, from version, applied-to, reviewed-up-to. engagement_versions says how things are now; decision_log says everything that happened to get there. Queried by engagement, by firm, or by version.

The version of an engagement only changes on create, apply, or decline, and all three go through the engagement system:

"The same system which loads engagements is also responsible for handling engagement creation, and for processing the user's accept/decline decision."

Backfill (existing engagements, one-off)
  1. Inventory (cheap): list each firm's engagements (id, name) and insert one row per engagement in engagement_versions with status "Verifying…". That table is the work queue; no separate queue is needed.
  2. Prioritize: recently opened engagements first; closed engagements from prior years last or excluded.
  3. Workers (per region): take the next "Verifying…" engagement, load it read-only (~1 min), read the three values it stores (template ID, version, revision), write them with the newer-revision rule, mark it verified. Each worker uses credentials scoped to the firm it is processing (D2). Nothing else is read: the template ID tells which product's releases to compare against, the version is the comparison base, the revision prevents stale overwrites.
  4. Load control: a global concurrency cap per region, a small per-firm cap (a large firm cannot starve small ones), more workers during each firm's off-hours (its own time zone), and automatic slow-down or pause if user-facing engagement loading degrades.
  5. Failures: retry with backoff; after 3 attempts the row is marked "Error" and an alarm fires. Progress lives in engagement_versions, so a crash resumes where it stopped. Engagements opened by users in the meantime are verified by EngagementOpened and skipped.
  6. Tracking: per-firm progress (verified / total / errors) on a dashboard.

Order of magnitude (assumed: 1,000 firms × 300 engagements, half of them closed): 150,000 loads; 100 concurrent loads → 6,000/hour → ~48,000 per 8-hour night → about 3 nights. Rollout: pilot with a few small firms to measure real load time and user impact, then waves. The same job is reused to onboard new firms and for the sampled drift check.

Until an engagement is verified, its row shows only its name, with template and version blank and status "Verifying…". It is never reported as "up to date", and the engagement itself stays fully usable: only the pending-update column waits.

Consequences
  • (+) The list and its pending updates are computed without loading any engagement file.
  • (+) Publishing a version is one row in template_releases; the cost does not grow with the number of engagements.
  • (−) The index is a copy and can drift; see failure notes below.
  • (−) During the backfill some engagements are in "Verifying…".
  • (−) template_releases duplicates metadata from the template store; it can be dropped if the store already lists versions cheaply.
Failure notes
  • Lost update (decision saved, our tables not updated): impossible by construction. The hook inside the engagement management system writes engagement_versions and decision_log in the same transaction as the engagement change, because they live in the same firm database. Changed: an earlier version used an outbox plus a separate event processor; removed as unnecessary once the tables were placed in the firm database (D2).
  • Stale overwrite (the backfill reads v3, a user applies v4 during that minute, the backfill then writes v3): every write to engagement_versions carries the engagement's revision number and is applied only if newer. The same rule covers duplicate or out-of-order events.
  • Drift detection: a periodic check reloads a small sample of engagements per firm and compares with engagement_versions.
Assumptions
  • Listing a firm's engagements (id, name) is cheap; only reading the template and version inside them is expensive.
  • An engagement can be loaded read-only, with no side effects, for the backfill.
  • Stored engagements carry a revision number or last-modified marker.
  • Closed engagements from prior years do not take template updates, so the backfill can leave them for last.
  • The template store holds each version's full content (inferred: templates are "zip archives of structured JSON data" and engagement creation "retrieve[s] the template file" from it).
D2

Where engagement_versions and decision_log live and how firm isolation holds end to end

Decided
"engagement content is client-confidential, and the pending-update data this feature introduces is derived from a template store shared across every firm. Whatever tracks and surfaces that state must enforce firm-level isolation as a structural property (not just an application-layer filter), must restrict who can see or act on a firm's pending updates to users authorized for that firm, and must respect any data-residency requirements the firm's engagement data is already subject to."
"Engagement files, which are stored in their own customer-specific databases."
What is confidential

engagement_versions (which engagements a firm has, i.e. its clients) and decision_log (who decided what) are confidential. template_releases (template, version, date) is Caseware's own data, identical for every firm, and stays shared (D3).

Options
OptionVerdict
AOne central database, rows keyed by firm_idRejected: exactly the application-layer filter the brief rules out; one region for everyone breaks residency
BNew tables inside each firm's existing databaseChosen: isolation and residency are inherited from a boundary that already exists
CA new database per firm for this feature onlyRejected: same isolation as B, but duplicates per-firm infrastructure
Decision: isolation along the whole path, not only storage

The requirement covers "whatever tracks and surfaces that state", so every component that touches firm data works with credentials that can only open that firm's database.

  • Change summaries are generated from the template diff only, with no firm data, so they can be shared.
Consequences
  • (+) Isolation and residency are properties of where the data and the processing live, not of a WHERE clause.
  • (+) Firms scale independently: a large firm does not slow down a small one.
  • (−) The new tables must be migrated into every firm database, rolled out gradually firm by firm.
  • (−) The global view for monitoring is an aggregation of per-firm counts, not a direct query.
Assumptions
  • New tables can be added to each firm's database.
  • Existing per-firm authentication can be reused, and database credentials scoped to a single firm can be obtained.
D3

How a newly published version reaches the user

Decided
"Users need to see at a glance which of their engagement files have pending updates […] provide users with that information in an up-to-date manner"
"a single update can affect every firm using that product at once."
Reading of the requirement

"Up-to-date" means the list is correct whenever the user looks at it: a version published minutes ago is already shown as pending. The brief does not ask for active notifications (email, push); they are an optional extension that the same event enables.

Options
OptionVerdict
AFan out on publish: find every affected engagement in every firm and mark itRejected: work grows with the number of engagements; one publish becomes a large cross-firm job
BPublish hook → queue → one row in template_releases; pending computed on read (engagement_versions compared with template_releases)Chosen
Flow
  PUBLISH   1. Content team publishes "Audit Canada v5" (template store, as today)
            2. Hook on the template store emits "Audit Canada v5 published"
            3. The message waits in a queue (nothing is lost if the consumer is down)
            4. Pending Updates Service adds a row to template_releases  → seconds, no engagement loaded

  READ      5. A user of Firm ABC opens the engagement list
            6. The service reads engagement_versions (Smith → Audit Canada v3)
               and template_releases (latest v5)
            7. v3 < v5  →  "Smith 2026: 2 pending updates"

  DECIDE    8. The user applies or declines (engagement system, as today)
            9. In the same transaction, the hook sets engagement_versions (Smith → v5)
               and appends to decision_log
Consequences
  • (+) Publishing costs one row, regardless of how many firms or engagements use the template.
  • (+) There is no ordering problem: a version published before an engagement is verified is already in template_releases and shows up as soon as engagement_versions knows the real version.
  • (+) template_releases holds no client data (template, version, date), so a single shared table is enough; only engagement_versions and decision_log are per firm (D2).
  • (−) The user only sees a new version when they look at the list; there is no active alert unless the optional notification is added.
  • (−) A lost or delayed publish message would hide a version: the queue retries, and an alarm fires if template_releases falls behind the template store.
Change (2026-09-24): seed template_releases at launch

Found in review: template_releases is new and starts empty, and the hook only reports versions published after it is enabled. Every version already in the template store at launch would be missing, so an engagement on v3 with v4 already published would show "Up to date", and v5's summary (diffed against v4) would hide v4's changes. Fix: when the hook is enabled, copy the list of existing versions from the template store into template_releases once (through the same queue, so processing stays idempotent on template + version). It must finish before the read API is enabled; it does not need to finish before the backfill, because pending is computed on read. It is fast: the template store is quick to read, and no engagement is loaded.

Assumptions
  • The template store can list the existing versions of each template (the brief only states retrieval "given a template ID and a version"; the reconciliation alarm already relies on this).

The concrete AWS messaging service is an implementation choice, deferred.

D4

Accumulated updates and what "decline" means

Decided
"Consider how to handle the scenario where multiple template updates accumulate before the user makes the accept/decline choice."
Options
OptionVerdict
AOne decision per version, oldest firstRejected: forces the user through intermediate versions that no longer matter
BOne accumulated decision to the latest; declining walks back one version at a timeChosen
Decision
  • Which versions are pending: floor = max(current, declined-up-to); pending = template_releases rows for the engagement's template with version > floor. Ordered by version number (dates are for display only).
  • One review covers all pending versions. The user either applies up to a version k (default: the latest) or declines all. Declining the latest walks the UI back one version at a time so the user can stop at k. Walking backwards is the only valid order: versions are cumulative, so v5 cannot be applied without v4, but the engagement can stop at v4.
  • Recorded once: the whole review is one event, UpdateReviewed(applied_to = k | none, reviewed_up_to = latest pending). Intermediate walk-back steps are UI only, so nothing is lost if the user leaves mid-review.
  • Comparison base: always the engagement's real current version. The summary for target k lists every version in (current, k] and flags those at or below declined-up-to as previously declined.
  • declined-up-to is a watermark that only rises (max()). Only versions above it are pending, so a declined version is not offered again. Declines live only in our tables; the backfill never touches them.
Example
  Smith 2026 is on v3. v4 and v5 are published.
    "Apply v3 → v5?"   Decline →  "Apply v3 → v4?"   Approve
    → one event: applied_to = v4, reviewed_up_to = v5  →  current = v4, declined-up-to = v5

  v6 is published (built on v5, so it carries v5's changes).
    floor = max(v4, v5) = v5, so only v6 is pending. Compared from the real version: v4 → v6.
    ▸ New in v6
    ▸ Previously declined (v5), would be included
    Decline →  declined-up-to = v6; v5 is not offered again.
Consequences
  • (+) One click in the common case (accept everything); full control when declining.
  • (−) Declining across many accumulated versions can take several steps.
  • (−) Applying a newer version brings back previously declined changes; the summary must make that explicit.
  • The watermark drives the logic; decision_log answers "what has this firm decided over time".
Assumptions
  • Version numbers increase monotonically per template.
D5

How the human-readable summary is generated

Decided
"You can assume that you have access to a quick and reliable way to compare two different versions of the same Product Template and extract a JSON diff. However, the users are non-technical and would strongly prefer something human-readable."
Options
OptionVerdict
AShow the raw JSON diffRejected: users are non-technical
BDeterministic rules per change typeRejected: requires knowing the internal template schema, which we do not; brittle as templates evolve
CLLM summary grounded in the old template + the diff, with deterministic checks only where they are obviousChosen
Decision
  • When: at publish time (not on demand), once per version against the previous one (v4 → v5), inside the publish flow (D3). Nobody waits, the content team can review before customers see it, and cost is one LLM call per release. Until a summary is ready or approved, the update still shows as pending with "Summary in preparation".
  • Accumulated versions (option A, chosen): a user on v3 sees the v4 and v5 summaries in order; a user on v4 sees only v5. Both read the same stored rows. Elements changed in more than one pending version are flagged "changed again in v5" by comparing diff paths (deterministic, no LLM). Rejected option B: a net summary per (from, to) pair generated on demand, because users would wait, pairs multiply, and the content team could not review them in advance.
  • Storage: release_summaries, one row per published version: template, version, from-version, summary text, exact change list (C1, C2…), review status, model and prompt version, generated-at. Shared by every firm (no client data). The "previously declined" label is computed at read time from each engagement's watermark, not stored.
  • Input: the JSON diff plus only the sections of the old template that the diff touches (extracted by following each change's path), so the model can name things ("procedure 12" → "Lease review") without reading the whole archive.
  • Grounding check (the only deterministic step): each diff entry gets an ID (C1, C2…); the summary must cite them. Code verifies that no cited ID is invented and that every change is covered. On failure: regenerate once, then route to human review.
  • Presentation: labelled "AI-generated"; the model never recommends apply or decline.
  • Data boundary: the model only sees Caseware template content, never firm data (D2).
Rollout and evaluation
  1. Before production: generate summaries for real historical publications (all versions are stored); the content team grades them. That set becomes the regression suite for any prompt or model change.
  2. Launch: the content team approves each summary before customers see it (~one per product per week).
  3. Steady state: sampled review plus user feedback, once measured quality is consistently high.
Consequences
  • (+) Readable summaries without encoding the template schema in rules.
  • (+) Cost is tiny: one generation per publication, not per firm or engagement.
  • (−) Non-deterministic output: mitigated by the citation check, the evaluation set, and human review at launch.
  • (−) The citation check proves coverage, not correctness of wording; that is what human review and the evaluation set are for.
D6

Rollout order, exit criteria and operational thresholds

Decided
"Whatever you propose has to hold up under real usage, not just work in a demo with a handful of engagements."
"you should be able to tell, without waiting for a user to report it, how many engagements are affected by a newly published update, whether the pending-update check is actually running for every firm, and what a firm's history of apply/decline decisions has been."
Context

Review against common design-doc practice (online migrations: expand → capture changes → backfill → verify → cut over; FMEA-style failure tables with detection; three-layer LLM evaluation) found that the plan had no exit criteria, overlapping steps 1–2, no verification before users see the data, and that tests, alerts and failure modes lacked concrete thresholds and detection.

Decision
  • Plan order: tables → capture new changes (engagement hook, listener, launch copy of existing versions) → backfill → verify hidden (pending computed but not shown, drift sample) → show to users (pilot, then waves). Summaries run in parallel. Each phase has a "done when" criterion; rollback is the per-firm flag (only additive tables and hooks).
  • Why capture before backfill: the backfill reads a snapshot; any create/apply/decline during it must already be written by the hook (in the firm's own database) or it would be lost.
  • Reconciliation (D3) no longer only alarms: it copies missing versions into template_releases, the same mechanism as the launch copy.
  • Failure table gains "effect" and "detected by"; "impossible by construction" replaced by the explicit flip side: our write shares the engagement transaction, so a failure on our side fails the user's action. Recorded as a tradeoff.
  • LLM vs. rule-based summaries added to the tradeoff list (from D5).
  • The "double submission" row was dropped from design.md for length; the behaviour stands: reviews are idempotent on (engagement, reviewed_up_to, revision).
Consequences
  • (+) Every phase is independently deployable, verifiable and reversible.
  • (−) The hidden verification phase delays what users see by the drift-check window.
  • (−) The thresholds below are starting points, not measured values; the pilot should recalibrate them.
Assumptions
  • Sizing: 1,000 firms × 150 open engagements, 100 concurrent loads (same as D1).
  • Thresholds (when the backfill counts as done, how long the pilot runs, when summaries move to sampled review, alert limits) are set during the pilot; the brief gives none.
